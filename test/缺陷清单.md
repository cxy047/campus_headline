## BUG-001 | S2 严重：RoleInterceptor 路径配置错误，新闻审核接口完全不受保护

| 字段 | 内容 |
|------|------|
| **标题** | RoleInterceptor 拦截路径写错，任何登录用户都能直接审核新闻 |
| **重现步骤** | 1. 用普通用户账号登录（非 admin） 2. F12 查看 Cookie 取 JSESSIONID 3. Postman 发送 GET 请求：`http://localhost:8080/campus_headline/news/auditPass?id=5` |
| **实际结果** | ⚠️ **审核成功！** 新闻状态从 pending 变为 pass，页面重定向到审核列表 |
| **预期结果** | RoleInterceptor 拦截，返回 403 "无权访问：仅管理员可执行此操作" |
| **根因定位** | `springmvc.xml` 第 62-64 行（修复前）RoleInterceptor 配置：`<mvc:mapping path="/news/audit"/>`、`/news/publish`、`/news/draft` 但 **NewsController 实际路径是** `/news/submitAudit`、`/news/auditPass`、`/news/auditReject`——**路径完全不匹配！** |
| **修复位置** | `src/main/resources/springmvc.xml` RoleInterceptor mapping 部分 |
| **修复方案** | 把 `/news/audit`、`/news/publish`、`/news/draft` 改为真实路径：`/news/submitAudit`、`/news/auditPass`、`/news/auditReject` |
| **修复证据** | [evidence/BUG-001-拦截器路径配置.md](./evidence/BUG-001-拦截器路径配置.md)（springmvc.xml 第 62-64 行修复前后对照） |
| **状态** | ✅ Fixed → Verified → Closed |
| **验证用例** | TC-B10 |

## BUG-002 | S2 严重：评论删除缺少 RoleInterceptor 保护，任何登录用户可删任意评论

| 字段 | 内容 |
|------|------|
| **标题** | 评论删除仅需登录，不校验操作者身份（本人/管理员） |
| **重现步骤** | 1. 用户 A 登录并发表一条评论 2. 用户 B 登录 3. Postman 发送 GET 请求：`/comment/delete?commentId=xxx`（commentId 为用户 A 的评论） |
| **实际结果** | ⚠️ **删除成功！** 数据库 comment 记录被物理删除，重定向到原页面 |
| **预期结果** | CommentController.delete 方法应校验：当前用户是评论作者 或 role=admin，否则拒绝删除 |
| **根因定位** | 双层缺陷：(1) RoleInterceptor 完全没配置 `/comment/delete` 路径；(2) CommentController.delete 方法里没有身份校验逻辑，直接按 commentId 删除 |
| **修复位置** | `springmvc.xml` + `CommentController.delete()` |
| **修复方案** | (1) RoleInterceptor 增加 `<mvc:mapping path="/comment/delete"/>`（注意 comment/add 需登录但非 admin 也能发，所以不加 RoleInterceptor）；(2) delete 方法里校验 Session 中的 loginUser.id == comment.userId || loginUser.role == admin |
| **修复证据** | [evidence/BUG-002-评论删除身份校验.md](./evidence/BUG-002-评论删除身份校验.md)（CommentController.delete 传参 + CommentServiceImpl.delete 身份校验） |
| **状态** | ✅ Fixed → Verified → Closed |
| **验证用例** | TC-E05 / TC-H05 |

## BUG-003 | S3 一般：写操作用 GET 请求，存在 CSRF 风险

| 字段 | 内容 |
|------|------|
| **标题** | 删除/审核/点赞等写操作全部用 @GetMapping，触发即执行，用户访问恶意页面会被静默调用 |
| **重现步骤** | 构造 HTML 页面：`<a href="http://localhost:8080/campus_headline/news/delete?id=5" onclick="alert('恭喜中奖！')">点我抽 iPhone</a>`，登录管理员账号点击链接 |
| **实际结果** | ⚠️ **新闻被删除！** 标签 href 跟随跳转，浏览器自动发 GET 请求，服务端执行了删除 |
| **预期结果** | 写操作用 @PostMapping + CSRF Token 校验，GET 请求只读不写 |
| **根因定位** | Controller 里写操作全部用 @GetMapping（NewsController.delete、VideoController.delete、TopicController.delete、LikeController.toggle、VideoController.auditPass 等） |
| **计划改造位置** | 所有 Controller 的写操作方法注解及对应 JSP 页面（News/Topic/Video/Like/Comment） |
| **计划方案** | (1) 写操作由 @GetMapping 改为 @PostMapping；(2) JSP 中删除、审核、点赞等链接改为 `<form method="post">` 或 AJAX POST；(3) 增加 CSRF Token 生成与校验，GET 请求只读不写 |
| **未实施原因** | 涉及 4 个 Controller 的 10 余个写接口及对应 JSP 页面，改造后需逐页回归验证，超出本期交付窗口；本期仅完成定级、根因定位与整改方案，代码未改动 |
| **状态** | ⏳ Open（方案已定，待实施），未进入 Fixed |
| **验证用例** | TC-H01（改造完成后复测） |

## BUG-004 | S3 一般：文件上传路径 `file:` 前缀与 Tomcat 10 不兼容

| 字段 | 内容 |
|------|------|
| **标题** | springmvc.xml 静态资源映射 `location="file:${user.home}/campus_upload/"` 在 Tomcat 10.1 下 404 |
| **重现步骤** | 1. 项目从 Tomcat 9 升级到 10.1（Servlet API 从 javax 改为 jakarta）2. 上传文件成功（物理落盘没问题） 3. 浏览器访问 `/upload/xxx.jpg` |
| **实际结果** | ⚠️ **404 Not Found！** file: 路径无法被 Tomcat 10 的 classloader 正确解析 |
| **预期结果** | 上传文件能通过 `/upload/**` 正常访问 |
| **根因定位** | Tomcat 9→10.1 升级后 `StandardServletMultipartResolver` + `mvc:resources location="file:..."` 组合行为变化，file: 前缀需加 `file://`（3 斜杠）或改用 `file:/` |
| **修复位置** | `springmvc.xml` 第 26-27 行 |
| **修复方案** | `location="file:/${user.home}/campus_upload/"` 加一个斜杠变成 file:/ 而非 file: |
| **修复证据** | `src/main/resources/springmvc.xml` 第 26-27 行改为 `file:/` 前缀；`/upload/**` 另由 `UploadController.serve`（第 31 行）提供访问与 Range 分段支持；访问截图待补，见 [evidence/README.md](./evidence/README.md) |
| **状态** | ✅ Fixed → Verified → Closed |
| **验证用例** | TC-F06 |
